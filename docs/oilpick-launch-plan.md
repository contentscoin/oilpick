## Phase 1. 디자인 (W2–W5)

### 1-1. 디자인 원칙 (리서치 기반)
1. **홈 = 시세 + 버튼 하나.** 올수 UX 리스크(정보 밀도 과다)의 반대로 간다.
   사장님이 앱을 여는 이유는 단 하나 — "오늘 얼마 받나".
2. **숫자가 주인공.** 시세, 예상 포인트, 수거비는 화면에서 가장 크고 굵게.
3. **상태는 항상 보이게.** 진행 중 수거 건은 배달앱처럼 타임라인 + 지도로.
4. **50대 사장님 기준.** 최소 폰트 16px, 터치 타깃 48px 이상, 전문용어 금지
   ("에스크로" ❌ → "배송완료 시 지급 확정" ⭕)
5. **신뢰 장치 노출.** 라이더 인증 카드, 현장 사진, 계량 확인은 디자인적으로 강조.

### 1-2. 브랜드 아이덴티티
- 컬러 제안:
  - Primary: **딥 그린 (#1B7A43 계열)** — 순환자원/친환경. 올수(노랑)와 차별화
  - Accent: **앰버/골드 (#F5A623 계열)** — 기름·포인트·돈의 은유. 시세 숫자, 포인트, CTA에만 사용
  - Semantic: 상승 빨강/하락 파랑 (국내 시세 관례), 상태별 컬러 (대기 회색/진행 파랑/완료 초록)
- 타이포: Pretendard (국문 가독성 + 무료 라이선스), 숫자는 tabular figures 적용
- 아이코노그래피: 라운드형 두꺼운 스트로크 (친근함), 기름통·저울·오토바이 커스텀 아이콘 5종

### 1-3. 디자인 시스템 (W2–W3)
`packages/ui`에 1:1 대응할 토큰/컴포넌트 정의:
- 토큰: 컬러, 타이포 스케일, 스페이싱(4px 그리드), 라운드, 그림자
- 컴포넌트 (우선순위순):
  1. 시세 카드 (현재가 + 등락 + 스파크라인)
  2. 주문 상태 타임라인 (5단계 스텝퍼)
  3. 콜 카드 (라이더용: 거리/수량/수거비)
  4. 포인트 잔액 카드 (확정/보류 구분)
  5. 하단 탭바, 버튼(대형 CTA/보조), 입력(수량 스테퍼), 바텀시트, 토스트/다이얼로그
- 다크모드는 런칭 범위 제외 (라이트 온리)

## Phase 2. 개발 (W3–W10, 2주 × 4 스프린트)

W3–W4는 디자인과 병행: 디자인 의존 없는 백엔드/인프라 먼저.

### Sprint 1 (W3–W4): 기반 공사
- 모노레포 스캐폴딩 (pnpm workspace + Turborepo): apps/user, apps/rider, apps/admin, packages/ui·core
- Supabase 스키마 v1 마이그레이션: users, supplier_profiles, rider_profiles, price_ticks,
  pickup_orders, order_events, point_ledger, withdrawals, depots, notifications
- RLS 정책 전 테이블 적용 (역할별 접근 통제 — 보안 리뷰 필수 항목)
- Auth: 전화번호 OTP 가입/로그인, 역할 분기
- Edge Function: 포인트 원장 코어 (`ledger_post`: EARN/HOLD/RELEASE/WITHDRAW/ADJUST,
  잔액은 원장 집계 뷰로만 계산, 클라이언트 직접 쓰기 금지)
- CI 구축, dev/prod 환경 분리
- **DoD**: 가입→역할별 빈 홈 진입, 원장 단위 테스트 통과

### Sprint 2 (W5–W6): 핵심 플로우 — 주문 상태머신
- 수거 요청 생성 (U3→U5): 수량, 주소, 시세 스냅샷
- 매칭 Edge Function: PostGIS 반경 검색 → 온라인 라이더 푸시 브로드캐스트 → 선착순 수락
  (락으로 중복 수락 방지) → 미수락 시 반경 확대 재시도
- 상태머신 구현: REQUESTED→ACCEPTED→ARRIVED→PICKED_UP→DELIVERED→COMPLETED
  + CANCELLED/DISPUTED, 모든 전이는 order_events 기록
- 라이더 앱: 콜 대기/수락/운행 화면 (R2–R6)
- 사용자 앱: 매칭 대기/진행 현황 (U6–U7), Realtime 구독으로 상태 실시간 반영
- FCM/APNs 푸시 연동 (배정/도착/완료)
- **DoD**: 실기기 2대로 요청→수락→상태 전이 E2E 시연

### Sprint 3 (W7–W8): 돈의 흐름
- 계량 확정 플로우: 라이더 입력 + 사진 업로드(Storage) → 사용자 확인(U8) → 확정
- 포인트 지급 로직: PICKED_UP 시 사용자 EARN + 라이더 HOLD, DELIVERED(집하장 QR 스캔) 시 RELEASE
- 시세 관리: 관리자 시세/수거비 설정 → price_ticks 기록 → 사용자 홈/그래프 반영
- 포인트 지갑 (U11, R8): 잔액, 원장, 확정/보류 구분
- 출금 신청 (U12) → 관리자 승인 큐 (이체는 수동 처리로 시작, 자동이체 API는 런칭 후)
- 라이더 인증: 서류 제출 (R1) → 관리자 검수 → 인증 카드 QR (R9)
- **DoD**: 원장 감사 쿼리로 "모든 주문의 포인트 합계 = 지급 규칙" 검증 통과

### Sprint 4 (W9–W10): 관리자 완성 + 앱 패키징
- 관리자 대시보드: 실시간 지도 (진행 주문 + 라이더 위치), 주문/회원/정산/집하장 관리 전체
- 분쟁 플로우: 사용자 이의신청 → DISPUTED → 관리자 중재 (수량 조정 → ADJUST 원장)
- 라이더 위치 업로드 (운행 중 15초 간격) + 사용자 지도 표시
- Capacitor 패키징: 아이콘/스플래시, 딥링크, 푸시 권한 온보딩, Android/iOS 실기기 테스트
- 예외 처리 일제 점검: 네트워크 끊김, 콜 만료, 라이더 노쇼 재배차, 취소 정책
- **DoD**: TestFlight / Play 내부 테스트 트랙 업로드 완료

## Phase 3. 통합 QA & 클로즈드 베타 (W11–W13)

### QA (W11)
- 시나리오 테스트 매트릭스: 역할 3 × 핵심 플로우 8 × 예외 케이스 (총 ~60 케이스 문서화)
- 포인트 원장 침투 테스트: 동시 수락, 이중 지급, 음수 잔액, RLS 우회 시도
- Supabase advisors (보안/성능) 점검, 부하 테스트 (동시 콜 브로드캐스트 100건)
- 접근성: 폰트 크기, 명도 대비 (사장님 연령대 고려)

### 클로즈드 베타 (W12–W13)
- 대상: 실제 매장 5–10곳 + 수거업체 2–3곳 (단일 지역 집중 — 예: 부천/인천 1개 구)
- 회사가 직접 집하장 1곳 운영, 시세는 보수적으로 설정
- 측정: 요청→수락 소요시간, 수거 완료율, 계량 이의율, 포인트 문의 건수, 앱 크래시
- 베타 피드백 반영 스프린트 (W13): UX 마찰 상위 5개 수정
- 이용약관/개인정보처리방침 법률 검토 완료본 앱 반영

### 베타 종료 게이트 (충족 못 하면 런칭 연기)
- [ ] 수거 완료율 ≥ 90%
- [ ] 요청→수락 중위 시간 ≤ 10분 (베타 지역 기준)
- [ ] 포인트 원장 불일치 0건
- [ ] 크래시 프리 세션 ≥ 99%
